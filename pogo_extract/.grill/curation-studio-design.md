# Curation Studio - design (generated 2026-06-08)

**Curation Studio — a standalone, per-category collection-curation suite added to the PoGo dashboard**

## Architecture

Lives as a NEW second page inside the existing Flask app dashboard.py — same process, same 127.0.0.1:8765 bind, same `pokemon.db` — reached by a new route `GET /studio` returning a new `STUDIO_PAGE` HTML string, with a small "Curation Studio" link added to the existing header (the only edit to existing markup; the entire current single-page control center stays byte-for-byte at `/`). Adding a route + a page constant cannot regress the existing page. It reads data READ-ONLY: every Studio endpoint (`/api/studio/*`) opens sqlite with `?mode=ro` (or a normal connection that only ever SELECTs), joins `pokemon WHERE in_bag=1` with `system/analysis/policy_reasons.json` (the uid→reason map the engine already writes) and `legacy_accurate.json`, and decodes ids in Python using the existing `form_enum.json`, `location_card_enum.json`, `move_id_to_name.json`, and `costume_forms.py` — no new heavy deps. Per-category knobs persist in a SEPARATE file `curation_config.json` (new `curation_config.py` accessor, mirrored on keep_config's defaults-merge/validate/atomic-write pattern) so curation tuning NEVER pollutes the live keep engine; the ONE exception is the shared caps/rosters that already exist in keep_config (gmax/dmax/shiny/rarity/xxl caps, legacy caps, origin_owners) — for those the Studio reads keep_config as the single source of truth and offers an explicit, confirmed "Apply to global engine" action that calls keep_config.write() (the same path the dashboard's Save uses), while all NEW granularity (per-species cap overrides, per-axis IV floors, sort keys, protect-toggles) lives only in curation_config and is applied by the Studio's own preview math, never silently by the engine. Each category gets the SAME shell: a left rail of that category's knobs + protect-toggles, a center gallery of specimen cards (sprite, species, IV numbers+labels, CP, badges), and a sticky right "Release candidates" panel showing exactly what the current knobs would put up for release, computed live by a shared `/api/studio/preview` that re-implements the relevant rule's cap+rescue logic on a read-only snapshot. A "cull" here is SAFE because it never writes the DB or pushes tags: the Studio only ASSEMBLES a reviewable release-candidate list and, on explicit confirm, writes those uids to a new `system/analysis/curation_release_candidates.json` queue; those uids then become eligible to flow into the EXISTING Transfer pile + preflight gate + manual in-game release — the Studio itself has no release power and no Frida. A hard cross-check runs before anything reaches the candidate list: any specimen the engine's policy_reasons.json keeps for a NON-category reason (hundo, shiny, legendary, origin E+F, legacy, PvP, etc.) is shown struck-through and cannot be selected, so the Studio can never propose releasing something the global engine protects.

## Non-regression guarantee

EXPLICIT GUARANTEE: the Curation Studio is PURELY ADDITIVE — nothing that works today is removed, replaced, hidden, or regressed. HOW: (a) The existing single-page control center at GET '/' and its entire `PAGE` HTML/JS string are NOT edited — all current panels and controls stay byte-for-byte: Configuration (every cap/PvP/legacy-default knob, rosters/weights JSON editors, keep-all rule toggles), Preview-impact, Save/Reset/Defaults/Export/Import, the diff-vs-defaults view, Run & Sync (Recrawl, Sync, dry-run, Pre-flight), the dry-run tag-diff preview, the Job log with live steps, the KPIs/donut/keep-reasons/server-tags/regions/Transfer-pile/Bag-search, and the 15-rule explainer. (b) The ONLY change to existing files is purely additive: a new `GET /studio` route, a new `STUDIO_PAGE` constant, the new `/api/studio/*` endpoints, and a single new <a> link in the header pointing to /studio — no existing route, function, query, or template branch is modified or deleted. (c) The keep engine is untouched: keep_policy.py and all 15 rules, build_tagsets.py and every one of the 12 server tags, preflight_transfer.py, prune_tags.py, refresh_evolve_shiny.py, reconcile_tags.py, and the whole recrawl/sync/preflight pipeline run exactly as before — the Studio never imports them to mutate state, only reads their JSON output (policy_reasons.json). (d) keep_config.json/keep_config.py remain the single source of truth and are written ONLY via the existing keep_config.write() path, only when the user explicitly clicks 'Apply to global engine' (with a confirm) — the default Studio workflow writes solely to the new curation_config.json, which the engine never reads, so curation tuning cannot drift a single keep decision. (e) Reads are mode=ro sqlite — the Studio cannot write pokemon.db. (f) The one optional engine edit (fixing build_tagsets.py:98 to call keep_config.origin_owners() instead of the hardcoded E+F list) is itself non-regressive — it makes the tag MATCH the already-existing keep decision and defaults identically to ['ethanmateovz','florandez'] — and is gated behind an open-question confirmation, not done silently.

The Studio config will carry a `sprite_base_cdn` string so the source is swappable without code edits, and the client lazy-loads with onerror chaining local->CDN->placeholder so a missing file is never a broken card. TRANSLATE ONLY internal code words into human names, each with the existing enum tables: (1) fresh_form numeric code -> form_enum.json (1479 entries, e.g. 322->'CharizardGmax', 1->'UnownA', 2585->'LaprasCostume2020') rendered as a clean costume/form name ('Lapras Costume 2020', 'Unown — A'); (2) fresh_loc_card_enum -> location_card_enum.json (280 entries; verified live values map cleanly, e.g. 242->'Lc2026RiodejaneiroCarnival001'->'Rio de Janeiro Carnival 2026', 133->'LcSpecialbackgroundExtra202502', 89->'2025 GO Fest — Sword Crowned') by stripping the 'Lc'/'LcSpecialbackground' prefix and inserting spaces before capitals/years; (3) special_bg_id (only ~5 distinct in-bag: 0,1,256,65536,119,65) -> a tiny hand-built BG_NAMES table ({1:'Event background',256:'Zekrom/Reshiram event background',65536:'Kyurem event background',119:'…',65:'…'}) since these are flag-style ids with no enum file; (4) move ids (move1/2/3) -> move_id_to_name.json (371) then prettified ('HYDRO_CANNON'->'Hydro Cannon') for the Legacy category, with the legacy_moves[] array coming from legacy_accurate.json; (5) engine rule names from policy_reasons.json -> plain 'why kept' phrases via a RULE_LABELS map (variant_floor->'Top copy of its form', shadow_best->'Best shadow', shiny->'Shiny keeper', rarity->'Legendary/rare keeper', origin->'Traded from a trusted friend', xxl->'XXL showcase', dex_only->'Only one you own', pvp/pvp_spread->'Great/Ultra League rank', legacy->'Legacy move', hundo/nundo->'Hundo/Nundo'); (6) dex number used as a bare id in subtype labels -> always paired with species_name + sprite. Every Pokemon card therefore shows: sprite image + species name + decoded form/costume/background/location NAME (with its own thumbnail for backgrounds/location cards where available from the same CDN pattern) + labeled IV numbers + CP + player-word badges + a plain-English 'why kept' line.

## Fool-proofing

It is fool-proof and feels powerful for a teen/casual player through: (1) NOTHING destructive in the Studio — the only output is a reviewable proposal queue in a JSON file; there is no release/transfer button anywhere in the Studio, and actual release still requires the existing live pre-flight + manual in-game tap. (2) Hard protection rendering — any specimen the engine keeps for a reason outside the current category is shown struck-through with its real reason ('Kept: shiny, location card') and its checkbox is disabled, so a beginner literally cannot select a mon the global engine protects. (3) Hundo/Nundo/Shundo tripwire — if a proposed candidate set contains a 15/15/15, 0/0/0, or shiny-hundo, the 'Add to release candidates' button is disabled with a red explainer; mirrors the keep_policy abort. (4) Confirmations + Undo — adding to candidates shows a toast with a 5-second Undo; the candidate panel has per-row remove and Clear-all; the only engine-touching action ('Apply to global engine') is a separate, clearly-labeled button behind a confirm dialog that names exactly which cap changes from X to Y. (5) Two truthful numbers always — every preview shows BOTH 'raw over-cap' and 'net after rescue' so the user is never tricked into thinking they're losing 11 Gmax when the real releasable set is 4. (6) Friendly empty/loading states — each category shows a skeleton shimmer while the RO query runs; an empty release queue shows 'Nothing flagged — your collection is within your caps. Tighten a cap or lower an IV floor to find duplicates.'; a category with no over-cap shows 'All your <category> are keepers right now — this is a browse/audit view.' (7) Satisfying, responsive feedback — cap steppers and IV-floor sliders update the release count live (debounced client-side against the preview endpoint); selecting a card animates it into the right-hand queue; counts tween. (8) Reversible config — Tier-B curation knobs live in their own file with Reset-to-defaults and 'use global' (null) on every knob, so experimenting can't break the engine or lose the user's place. (9) Plain language for scary concepts — 'release candidate' not 'cull', 'these would go up for transfer (you still confirm each in the game)' not 'delete'. (10) Loading guard against races — every Studio write returns a clear 'a recrawl/sync is running, try again in a moment' instead of corrupting state.

## Full design

# Curation Studio — Design Document

## 0. One-line intent
A standalone, fun-to-use **collection curator** bolted onto the existing dashboard that lets the user browse each *special* category (Gmax, Dmax, Legendaries, Backgrounds/Locations, XXL, Shiny, Lucky/Traded, Legacy) by the attributes players actually care about, turn per-category knobs, and assemble a **reviewable release-candidate list** — which still flows through the existing pre-flight gate and manual in-game transfer. It never auto-releases anything and never touches the keep engine unless the user explicitly clicks "Apply to global engine."

---

## 1. Where it lives & why

**A new page in the SAME app**, not a separate process.

- New route `GET /studio` → returns a new `STUDIO_PAGE` HTML string (same hand-rolled, no-Jinja, single-file style as the existing `PAGE`).
- The only edit to existing markup is one link in the header: `<a href="/studio">Curation Studio →</a>`. The current control center at `/` is otherwise untouched.
- New endpoints are all namespaced `/api/studio/*` so they can't collide with the existing `/api/*` routes.

**Why same app:** the user already runs `python dashboard.py` and the memory explicitly says they want this "folded into the SAME suite … a new tab/module reading the same pokemon.db, ideally sharing keep_config." Same process means one DB path, one keep_config, one job lock to respect, zero new install steps.

**Why a separate PAGE (not a tab on the existing page):** keeps the blast radius near-zero — the existing control center's giant `PAGE` string and all its JS are not edited, so nothing there can regress.

---

## 2. How it reads data — strictly read-only

- Every Studio endpoint opens the DB read-only: `sqlite3.connect('file:' + DB + '?mode=ro', uri=True)`. It only ever runs `SELECT`. No Studio code path writes `pokemon.db`.
- It JOINs three things the engine already produces, so the Studio and the engine can never disagree about *why* a mon is kept:
  1. `pokemon` rows (`WHERE in_bag=1`) — the live bag.
  2. `system/analysis/policy_reasons.json` — the uid→[reasons] map `keep_policy.py` writes on every recompute (e.g. `["variant_floor","shiny"]`). This is the ground truth for "what keeps this mon."
  3. `legacy_accurate.json` (uid_hex + legacy_moves[]) for the Legacy category, and `move_id_to_name.json` to render move names.
- It NEVER reads `display_form`/`display_costume`/raw `bread_mode`/`is_gmax_dmax` (all NULL-unreliable per the analyses). It uses the **fresh_*** columns the engine uses: `fresh_shiny`, `fresh_alignment`, `fresh_bread_mode`, `fresh_form`, `fresh_costume`, `special_bg_id`, `natural_art_background`, `fresh_has_location_card`, `fresh_loc_card_enum`, `pokemon_size_category`, plus the RARE_PIDS roster (not `is_legendary`) for rarity.

---

## 3. How knobs persist — a separate `curation_config.json`

Two tiers, deliberately separated so curation tuning can't drift the engine:

**Tier A — shared with the engine (single source of truth = `keep_config.json`):**
the caps/rosters that already exist there: `caps.gigantamax/dynamax/shiny/rarity/xxl/cosmetic`, `legacy_species_caps`, `rarity_keep_all_pids`, `origin_owners`, `showcase_weights`. The Studio *reads* these from `keep_config` and shows them as the live baseline. Changing one in the Studio is an explicit, confirmed **"Apply to global engine"** action that calls `keep_config.write()` (same validated/atomic path the dashboard already uses). This is the only way the Studio touches the engine, and it's opt-in.

**Tier B — Studio-only granularity (new `curation_config.json` + `curation_config.py`):**
everything the engine has NO concept of today — per-species cap overrides, per-axis IV floors, per-category sort keys, the protect-toggles, owner per-cap, event-stack collapse, "redundant-with-other-axis" hide preference, group-by granularity. These live ONLY in `curation_config.json` and are applied by the Studio's own preview math. The engine never reads this file, so a curation experiment can't change a single keep decision until the user deliberately promotes a Tier-A value.

`curation_config.py` copies keep_config's hardened pattern verbatim: `DEFAULTS` dict, deep-merge over a user file, per-accessor `_int`/coercion so a hand-edit can't crash anything, `validate()` with bounds, atomic `write()`.

- **Browse/filter/sort:** the gallery groups by the category's collectible axis (species, or species+variant) and is filterable by every attribute in that category's filter list (§ per_category). Sort dropdown changes both display order and which copies fall below the cap line.
- **Live "what this would release" preview:** the right panel calls `POST /api/studio/preview` with `{category, knobs}`. ## 5. How "culling" stays SAFE (the core safety design)

This is the single most important guarantee. Releasing a Pokémon is irreversible and the user's memory is emphatic about pre-flighting the Transfer pile on every axis.

1. **The Studio cannot release anything.** It has no Frida, no in-game transfer, no DB write to `in_bag`. Its only mutation is appending uids to `system/analysis/curation_release_candidates.json`.
2. **Engine cross-check (hard gate at selection time).** Before any uid can be checked for release, the Studio looks it up in `policy_reasons.json`. If the engine keeps it for ANY reason outside the current category (e.g. a low-IV over-cap Gmax that's also shiny, or a dupe legacy that's also legendary), the card is rendered struck-through with the real reason ("Kept: shiny, location card") and its checkbox is disabled. The Studio can only ever propose releasing a mon whose *sole* keep-reason is the category being curated — exactly the "sole keeper" framing the analyses repeatedly call out.
3. **Hundo/Nundo/shundo tripwire.** If the candidate set would ever include a 15/15/15 or 0/0/0 (or a shiny hundo = "shundo"), the "Add" button is blocked with a red explainer, mirroring the keep_policy tripwire that aborts a sync if a hundo reaches Transfer.
4. **It flows through the EXISTING gate, not around it.** The candidate file is just a *proposal queue*. To actually transfer, those uids must still be picked up by the normal pipeline → land in the real Transfer pile → pass `preflight_transfer.py` (live Frida, every axis) → be released by hand in-game. The Studio adds a step *before* the existing safety chain; it removes none.
5. **Undo + confirmations everywhere.** Adding to candidates shows a toast with **Undo** (5s) and the candidate panel has a per-row remove and a "Clear all." Nothing is destructive; the worst case is a uid sitting in a JSON proposal file that the user can empty with one click.

## 6. Data integrity guards baked in (from the analyses)

- **Gmax/Dmax:** identify by `fresh_bread_mode` (==2 / ==1) ONLY; ignore raw `bread_mode`, `is_gmax_dmax`, `is_gigantamax_capable` (capability ≠ actual).
- **Rarity:** membership by RARE_PIDS roster, not the NULL-prone `is_legendary/...` columns (the columns miss 25 real rares).
- **XXL:** use `pokemon_size_category==5`, never `size_enum` (they disagree 228 vs 161).
- **cf() normalization:** the Studio re-uses the engine's `cf()` collapse (form-0 → species base) so per-(species,form) caps don't double-count the Chansey/Wailmer/Shellos form-0-vs-base split. Without this the Dmax/XXL caps would miscount.
- **Shiny:** read `fresh_shiny`, group per (species, cf-form) → 631 groups not 573 species.
- **Garbage art-bg:** the 6 mis-aligned `natural_art_background` sentinel rows are hidden by default (`hide_garbage_art_bg`), with a one-line "data note" so the user knows why a count looks off.
- **Origin drift bug surfaced:** the Origin screen explicitly notes that `build_tagsets.py:98` hardcodes the E+F owner list instead of reading `keep_config.origin_owners()`, so editing owners updates the keep decision but not the on-device "Traded by E+F" tag. The Studio's "Apply owners to engine" action will (as a tiny, additive fix) also patch that one line to call the accessor, killing the drift — flagged as an open question first.

## 8. Per-category specifics
See the structured `per_category` field for the view + knobs of each of the 8 categories. Highlights:
- **Gmax / Dmax / Shiny / Rarity / Legacy:** the cap rarely bites today, so the Studio's real value is letting the user set a *tighter* per-species/per-variant cap or an IV floor than the global engine dares — with the raw-vs-net-after-rescue preview making the true releasable set obvious.
- **Backgrounds/Locations & XXL:** effectively curation/audit browsers (caps don't bite at this scale) — group-by-variant to spot accidental dupes and confirm coverage; the only knobs that move a mon are lowering the cosmetic/XXL cap below a bundle size or turning off location_card_keep_all.
- **Lucky/Traded:** browse by origin owner; the load-bearing knob is `kept_owners` (E+F today) and a per-owner cap; "redundant-with-other-axis" hide focuses the ~16 mons origin solely protects.
