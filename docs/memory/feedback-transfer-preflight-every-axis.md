# Pre-flight Transfer on EVERY axis; read caps from keep_config; read deployment LIVE (2026-06-06)

A multi-failure session on the irreversible Transfer pile. The user was furious about repeated carelessness ("you're winging it... you're supposed to go deep every time... enumerate everything"). Hard-won lessons:

**1. Pre-flight EVERY keep axis, never a subset.** Costume Pikachu leaked into Transfer and I called the pile "safe" after checking only shiny/hundo/nundo/lucky/rank -- NOT costumes. "Safe to release" means checked against ALL of: costume/cosmetic (`fresh_costume`; form-encoded costume = `is_costume_form()` on BOTH `form` AND `fresh_form`; `fresh_natural_art_bg`; `costume_decoration_id`, normalizing TEXT `'0'`; `fresh_bread_mode` 1/2 = Dynamax/Gigantamax -- never `natural_art_background` or the retired `special_bg_id`, both garbage), shiny, hundo(45), nundo(0), lucky, legendary/mythical, traded, legacy, event, XXL, PvP gl/ul rank<=5 AND CP-viable, AND live deployment (see 4). A partial check presented as complete is the exact failure called out.

**2. Costume/cosmetic variants are CAPPED, not keep-all** (user choice 2026-06-06). **The NUMBER lives in `keep_config.json` and nowhere else — read it, never quote one from memory.** Each distinct (pokemon_id, form [cf-normalized in keep_policy], fresh_costume, fresh_natural_art_bg, decoration, bread 1/2) is its own variant; excess beyond the cap -> Transfer is EXPECTED. **I first flipped this to keep-all with NO authorization or changelog -- the user called that out as laziness. NEVER make a blanket policy change unilaterally; enumerate the real picture and let the user choose.**

**3. keep_policy tripwires (ABORT if one reaches Transfer): hundo, the chosen nundo of each look (duplicates are capped), and a viable top-rank PvP spread.** NOT costumes -- costume excess beyond the cap is legitimate.

**4. SUPERSEDED 2026-09-24 (user "3. sure"): NO GYM EXCUSE.** The live read below could only EXCUSE a keeper (GYM_LOCKED -> PASS -> Transfer tag -> releasable once knocked out of the gym), and it was the only reason the gate re-walked the bag mid-pass. preflight_transfer no longer reads deployment and never attaches; a keeper in a gym is a REAL_KEEPER. History: **Deployment (gym defenders) -- read LIVE off the proto, NEVER the DB.** A gym defender CANNOT be transferred (game-enforced); a deployed mon in Transfer is HARMLESS (the game blocks the release -- it just stays. This is why a deployed shiny Gyarados stayed in the bag when 405 other Transfer mons were released). The DB deployment columns (`is_deployed`, `deployed_fort_id`, `deployed_gym_lat/lng`) are UNRELIABLE: parsed from the stored `raw_proto_hex` snapshot; the string fields are the shared empty-string sentinel `0x7b81c1cf40` (unreadable offline) and coords are usually blank -- it caught 1 of 2 deployed mons and missed the one that mattered. **Read it LIVE:** walk the bag + read the PokemonProto gym-coord doubles at `proto+0x140` (lat) / `proto+0x148` (lng); non-zero = currently deployed. Verified 2026-06-06 -- a live Frida read found BOTH deployed shiny Gyarados the DB had as not-deployed. The pre-flight should read deployment live and flag deployed Transfer mons as "can't transfer / safe."

**5. Enumerate everything; verify against LIVE ground truth, not stale columns.** The recurring root cause was spot-checking one form/one source and trusting stale DB columns over the live game. The phone is rooted -- read the live state.

**TOOLING (2026-06-06):** the comprehensive pre-flight is codified in `system/scripts/preflight_transfer.py` -- it re-derives every UNCONDITIONAL keep axis from pokemon.db (hundo / the chosen nundo of each look / E+F-origin lucky-traded / legacy / event / mighty / adventure_effect / location_card / pvp_spread / dex_only_copy / dex_only_form / protected / favorite / shiny_ladder + rank<=5-viable incl. any viable chain stage (pvp_chain), and pvp_unknown when both ranks are NULL) AND reads deployment LIVE off the proto (gym coords 0x140/0x148), classifies each Transfer uid (PLAIN / COSTUME_EXCESS / SHINY_EXCESS / XXL_EXCESS / LEGACY_EXCESS / GYM_LOCKED=safe / REAL_KEEPER=alarm / EGG / MISSING_FROM_DB), and exits 1 on any non-gym-locked real keeper. It blocks keepers (+ EGG / MISSING_FROM_DB), never cap excess: since 2026-06-08 the shiny/costume/XXL caps are NOT re-derived as keepers (their `*_within_cap` replicas only annotate EXCESS labels and never FAIL) and a legendary alarms only if it earns another axis; but legacy (`_legacy_kept_uids`, per-species caps -> LEGACY_EXCESS) and location_card (`_loc_card_kept_uids`, per card) ARE re-derived cap-aware (2026-09-02), so a within-cap copy of either in the pile FAILS. It is FAIL-SAFE (Frida down -> can't clear gym-locked; gamemaster down -> over-protects any rank<=5). It AUTO-RUNS at the end of `pogo_pipeline.py` (prints `TRANSFER PRE-FLIGHT: PASS/FAIL`). ALWAYS gate the sync/release on its PASS.

**EVERY-RECRAWL VERIFICATION (2026-06-07) -- the user's standing requirement is "verify EVERYTHING every recrawl, never piecemeal or only-when-asked."** pogo_pipeline.py now AUTO-RUNS at its tail: (1) `system/scripts/preflight_transfer.py` (Transfer pile keeper-free across EVERY axis + LIVE deployment read off the proto), and (2) `system/scripts/audit_tags.py` (per-tag keep_policy-reason <-> build_tagsets-file consistency + bag partition). The recrawl Bash then runs `reconcile_tags.py` (server==DB==file) post-sync. audit_tags distinguishes EXACT tags (Hundo, Nundo, Traded by E+F), which MUST equal their keep-reason; RANKED tags (GL/UL Rank 1, Rank 2-5, Evo rank files), checked against gl_iv/ul_iv for leaks and misses; and LABEL tags (Legacy Moves, XXL), which may be a BENIGN SUPERSET of the keep-reason but must be keeper-free + contain every kept-for-reason mon. So a keeper-leak OR a keep_policy<->build_tagsets drift (the recurring Legacy-cap / XXL-form-vs-cf class) is caught EVERY recrawl, automatically. (XXL note: keep_policy groups by cf, build_tagsets by raw form -- a benign 1-mon superset today, e.g. a shiny XXL kept-by-shiny + XXL-labeled.)

**A cap RULE lives in several places (2026-06-08; 2026-09-02).** Cap VALUES live in `keep_config.json`, except the middle-stage cap `plain_line_preevo` = 2 (MIDDLE stages only), a hard-coded `keep_config.py` DEFAULT; every consumer reads `keep_config.cap`/`species_cap`, and `cap()` falls back to DEFAULTS for any key the json lacks. A cap RULE change must be mirrored in `keep_policy.py` AND `build_tagsets.py` (e.g. the XXL showcase ordering, build_tagsets.py:117) AND in `preflight_transfer.py` wherever the gate re-derives that axis: today legacy (`_legacy_kept_uids`) and location_card (`_loc_card_kept_uids`); only its shiny/costume/XXL `*_within_cap` replicas are informational. Why: an XXL rule change once updated keep_policy + build_tagsets but missed preflight's then-independent copy → 4 FALSE "XXL keeper in Transfer" alarms blocked the sync; capping location_card on 2026-09-02 made preflight report 17 phantom REAL_KEEPERs until it was mirrored. When a rule moves, grep every consumer (checklist in [[pogo-capped-vs-keepall-bug-class]]) and update every copy.

**RECRAWL FIRST, THEN SYNC (relearned 2026-06-08, the hard way).** I computed keep_policy + built tags + started the server sync off a STALE 5195-row DB while the LIVE bag was 5080 (the user had released ~115 mons between turns). prune's live bag-walk found 155 Transfer-file uids no longer live + did a partial write; I had to run the full recrawl (`pogo_pipeline.py`) and redo set_db→prune→reconcile, which converged (Transfer 218→88, all 12 tags server==DB==file). The registry procedure step 1 is literally "RE-CRAWL FIRST" for exactly this — the bag drifts EVERY turn. ALWAYS `pogo_pipeline.py` before any tag sync; never sync off a DB from a previous turn.

**PREFLIGHT lucky/traded = E+F-ONLY (aligned 2026-06-08).** `preflight_transfer._keeper_reasons` used to alarm on ANY `is_lucky`/`is_traded` (deliberately over-broad "over-protect the pile"). That FALSE-FAILED a legitimately-transferred shiny-displaced LUCKY Vanillite (owner VamsiVee) + traded Igglybuff (vgroover) — neither from E+F. keep_policy's ONLY lucky/traded keep axis is `origin` = ethanmateovz/florandez; the user treats luckies-from-others as NORMAL. Fixed: preflight flags lucky/traded ONLY when `owner in EF_OWNERS`. The `best_buddy` keeper-axis was also removed from preflight (the BB tag was nuked 2026-06-08; 0 sole-best_buddy mons — all kept by another axis). LESSON: a pre-flight that over-protects beyond the actual policy generates FALSE failures that block legitimate transfers — align its axes to keep_policy's real keep rules, don't invent broader ones.
