**PARTIAL BAG-WALK (2026-06-16, user: "WTF is this partial walk... imperfection is not tolerated").** `bag_walk` in pogo_il2cpp.py traversed the PokemonBagImpl LinkedHashMap (~4700 nodes) with `catch(e){break;}`, so when a `next` read faulted mid-walk the loop SILENTLY returned a partial map AS IF complete. That made reconcile_tags `--report` (and preflight/prune, all via `pg.walk_bag_protos`) read fewer tagged protos than really exist → phantom DRIFT that MOVED between runs (a different tag short on each walk = the tell). Partial walks = concurrent list mutation (bdwgc is non-moving). The walk must NOT stop the world (that froze PoGo, 2026-09-09: [[pogo-gc-world-freeze-2026-09-09]]). Completeness comes from the declared/walked/truncated check + retry; `walk_bag_protos()` RAISES rather than ever returning a known-partial map. Drift that is STABLE run-to-run is REAL (inherited tags from user-evolved pre-evos) and clears on a clean recrawl+sync. **Lesson: a walk that can silently return short is a BUG, not "instability" — never paper over it with re-runs.** (So the "first post-resume walk is partial" case below is caught + retried, not returned.)

Three fixes for the PoGo-Frida instability that wasted hours across many sessions (recurred 5x, 2026-05-16 → 2026-05-21):

1. **PID drift = Android's cached-app freezer killing PoGo when backgrounded.** PoGo gets killed at oom_adj ~900-955 when backgrounded (logcat shows `am_proc_died` + `freezing`), then re-launches on tap with a NEW pid, invalidating every Frida address. Fix: `cmd deviceidle whitelist +com.nianticlabs.pokemongo` and pin `/proc/<PID>/oom_score_adj=-900`. Also keep scripts FAST — a slow script (full liveness scan + 2000-line `bulk_tag.js` load) can get recycled mid-op; the lean pipeline finishes in ~7-9s and survives. **The cached-apps freezer is PERSISTENTLY DISABLED** via `adb shell settings put global cached_apps_freezer disabled` (user-approved 2026-06-06 — the global toggle, survives reboots). This ended an all-session PID-churn/frozen-write nightmare: tag-write prunes kept silently no-op'ing because Android had frozen PoGo's process (the ready_gate now reports `cpuset=/background -> [frozen]` and REFUSES the write rather than fake success — if writes won't land, check the freezer is off and that PoGo is genuinely foregrounded, NOT just window-focused; a just-foregrounded PoGo also reloads its bag, so the first post-resume walk is partial). Re-enable with `settings put global cached_apps_freezer default` if background battery drain matters.

2. **Use the IL2CPP liveness API for singletons** — `il2cpp_unity_liveness_calculation_from_statics(klass, ...)` returns exactly the live instances of a class, ~100x faster than a heap scan and with zero false positives. It replaced 60-90s hook-waits and brittle 69-candidate heap scans for PokedexImpl / TaggingRpcService / PokemonBagImpl. The pattern lives in `pogo_il2cpp.py` (`find_singleton`) + the pipeline's `step_singletons`. Liveness can occasionally return stale/proxy instances, so probe candidates (bag walk >100 entries; svc NumberOfTags 1-200; dex dict 500-4000) to pick the real one.

3. **"database is locked" = a leftover/interrupted python process still holds `pokemon.db`.** This came from an interrupted `compute_all_ranks.py`. `PRAGMA wal_checkpoint(TRUNCATE)` did NOT release it — find the holder via `Get-Process python*` (check command lines) and `Stop-Process -Id <pid> -Force`. Don't retry the locked operation in a loop.

4. **Tailscale ADB drop + dead Frida endpoint (2026-05-28).** Mid-session the Tailscale wireless ADB (`100.98.158.56:5555`) dropped; the phone was still on USB (`adb devices` showed serial `4A181FDAP0013G`) but the Frida endpoint had died with the link. `get_session()` then HUNG forever on `frida.attach` (an `adb forward`'s local socket accepts even when the remote end is dead, so a socket precheck can't detect it). Fixes now baked into `get_session()`: (a) `_resolve_device()` falls back ADB_TARGET → first USB device automatically; (b) the attach runs in a daemon thread with a hard **15s timeout** → raises instead of hanging. If attach times out, remember the endpoint is the ZygiskFrida gadget inside PoGo: check that PoGo is running, ZygiskFrida is loaded and Tailscale is up. There is no frida-server to restart.

**Why:** These are environmental, not logic, failures — fighting their symptoms per-command (re-attaching, retrying) is the slowness; applying the root fixes up front makes the session fast and stable.

**How to apply:** Freezer (global) and the deviceidle whitelist are persistent: verify them, don't re-apply. Only the per-pid oom pin is per-session. Build self-healing into long Frida drivers: catch `frida.InvalidOperationError`/`TransportError`, reconnect (adb connect + forward + re-attach via `pidof` poll), resume. Keep each script lean. On DB-lock, find+kill the stuck python PID. Relates to [[feedback-pogo-session-conduct]], [[project-pogo-extract]], [[pogo-il2cpp-internals]].

**2026-09-24: the shared liveness walk runs in C (CModule).** It was the AutoCatcher session's design, verified on the phone.
- **Why:** Frida has one JS lock for every script in the gadget. The old walk ran JS NativeCallbacks inside the stopped GC world. When the catcher's JS on UnityMain held that lock at the moment of the stop, the callback waited forever and PoGo froze.
- **Now:** `pogo_il2cpp.liveness_find_instances` builds `LV_SRC` once per script. Stop, alloc, from_statics, finalize and start all happen in C, and all state lives in a JS-allocated buffer. CModule statics sit on a read-only page in this build, and writing one SIGSEGVs PoGo.
- **Fallback:** if the CModule won't build, `liveness_find_instances_js` (the old walk) runs instead.
- **Verified:** C and JS gave identical singletons for TaggingRpcService and PokemonBagImpl.
- **Concurrency:** culls now run alongside the catcher. `full_audit.CATCHER_PAUSE_ENABLED = False` turns off the `/data/local/tmp/pogo_pause` handshake; the code is kept behind that flag.
- **Pre-existing hazard:** other scripts in the tree that bind `il2cpp_stop_gc_world` themselves (`_event_*`, dex_badge_probe, read_pokedex_liveness, _showcase_detail) still run JS in a stopped world. Don't run them while the catcher is attached.
